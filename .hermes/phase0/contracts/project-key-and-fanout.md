# Project key, prompt snapshot, and fan-out contract

Status: Phase 0 contract; no product implementation is contained in this file.

## Boundary and source anchors

Omarketing uses ordinary saved workflows and ordinary Comfy prompt submissions. A project is represented by the existing top-level Workflow folder for display/navigation and by an immutable backend-issued UUID `project_key` for identity. No Project API replaces Workflow management, and no save-completion hook passively creates or changes identity.

Fan-out is a temporary custom-widget submission mode. It uses one existing `ComfyApp.queuePrompt(number, N)` call and its existing per-iteration widget callbacks. It does not modify or patch Queue, History, Run, Shift+Run, Auto Queue, cache, failure, cancel, interrupt, or execution state.

Normative source anchors:

- `src/scripts/app.ts`: `QueuePromptOptions`, `ComfyApp.queueItems`, `ComfyApp.processingQueue`, `ComfyApp.graphToPrompt`, and `ComfyApp.queuePrompt`.
- In `ComfyApp.queuePrompt`, each iteration calls `beforeQueued`, then `graphToPrompt`, then awaits `api.queuePrompt`, then increments `queuedCount`, then calls `afterQueued`.
- In `ComfyApp.queuePrompt`, a submission exception breaks the batch before `queuedCount++` and `afterQueued` for that iteration.
- `src/scripts/api.ts`: `ComfyApi.queuePrompt`; `number === -1` maps to `front: true`, `number === 0` appends normally.
- `src/types/litegraph-augmentation.d.ts`: existing `IBaseWidget.beforeQueued`, `afterQueued`, and `serializeValue` callbacks.
- `src/types/comfy.ts`: existing extension `setup`, `nodeCreated`, and `loadedGraphNode` hooks.
- `.hermes/phase0/schemas/output-locator.v1.schema.json` and `.hermes/phase0/schemas/selection-manifest.v1.schema.json`: output/selection authority after execution.

None of those product source files is changed except the single extension bootstrap import permitted by `core-file-allowlist.md`.

## Project identity

### Canonical key

`project_key` is a canonical lowercase RFC 4122 UUID string generated by the backend using a cryptographically secure UUID implementation. The server, not the browser, chooses it. The server rejects nil UUIDs, noncanonical representations, and client-proposed project keys during issuance.

The top-level folder name and workflow path are locators, not identity. Renaming a workflow within the same top-level folder does not change the project. A different top-level folder is a different project binding even if its name or content is similar.

### Explicit issuance entry points

A key may be issued only through one of these user-visible Omarketing flows:

1. `official_template_copy`: the user copies an official Omarketing template into a new top-level Workflow path;
2. `project_context_initialize`: the user activates `프로젝트 설정` → `프로젝트 초기화` on an unbound Project Context custom node;
3. `rebind_as_new_project`: the user explicitly confirms a new blank project binding for a workflow copied/imported into another top-level folder.

Ordinary Save, autosave, Save As completion, rename, duplicate completion, import completion, and graph load never issue or rewrite a key by themselves.

The exact same-origin endpoints are:

- `POST /api/omarketing/v1/project-contexts:issue`
- `GET /api/omarketing/v1/project-contexts/{project_key}`
- `PUT /api/omarketing/v1/project-contexts/{project_key}`
- `POST /api/omarketing/v1/project-contexts:recover`

All are protected by the Phase 0 auth gateway. The server derives owner identity from the authenticated session. It never accepts owner identity from a body/header/query field.

The fan-out admission endpoint is:

- `POST /api/omarketing/v1/fanout-sessions:prepare`
- `POST /api/omarketing/v1/fanout-sessions/{fanout_request_id}:reconcile`

Its request contains `schema_version`, canonical Workflow locator, project key,
expected project-context and ReferenceSelection revisions, ordered selected
reference IDs, requested Queue position, and a client idempotency request ID.
The server revalidates ownership, selection membership, rights/capability,
cost/time envelope, and uniqueness. Its response contains the authoritative
context/selection revisions, one server-issued `fanout_request_id`, one
server-issued `run_key` shared by that fan-out action, the bounded snapshot lease and expiry,
and safe estimates. The browser never chooses an authoritative run key or
fan-out request ID.

The reconcile request contains the snapshot lease and client-observed callback
receipt. The server returns the authoritative accepted prompt ID/reference/run
tuples correlated by prompt admission and confirmed against existing Comfy
Queue, active execution, or History/job evidence, plus the never-accepted
references. A provisional prompt-admission record without corresponding core
job evidence is not counted as accepted. This route is required because core increments `queuedCount` before running
`afterQueued`, and another widget callback or Queue UI refresh can throw after
the backend already accepted a prompt. Frontend callback count alone therefore
cannot authorize a retry.

## Storage, revision, and recovery rules

- The backend custom-node package owns an atomic owner-scoped project-context store keyed by `(owner, project_key)`.
- The current value has a monotonically increasing integer revision. Successful updates use compare-and-swap `expected_revision`; conflicts return the latest safe revision and require an explicit reload/merge by the user.
- Accepted revisions are immutable for prompt snapshot lookup. Updating context creates a new revision; it does not alter a revision already referenced by an accepted prompt.
- The server stores the normalized top-level folder binding alongside the key. This binding is an authorization/consistency check, not the key itself.
- A missing or malformed key, inaccessible owner binding, missing server record, or top-level mismatch is an unbound state. Workflow editing/saving is allowed; execution is blocked with a safe recovery/rebind action.
- Authorization failures do not reveal whether a key exists for another owner. They use the same safe not-found/inaccessible response.
- Deleting a workflow does not automatically delete project context. History/output deletion and project-context deletion are separate and no project deletion lifecycle is introduced in MVP.
- A failed workflow save after successful issuance leaves the key in the in-memory node and the owner-scoped draft recoverable. Retrying the flow with the same `issuance_request_id` returns the same key. No save hook compensates by deleting it.

### Exact logical storage layout

The store root is the configured Comfy user-data root, resolved by the
backend, never a browser-supplied path:

```text
<COMFY_USER_DIRECTORY>/omarketing/v1/
└── owners/<owner_storage_id>/
    ├── projects/<project_key>/
    │   ├── binding.json
    │   ├── current.json
    │   └── revisions/<20-digit-revision>.json
    ├── issuance/<issuance_request_id>.json
    └── bindings/<sha256-of-normalized-top-level-folder>.json
```

`owner_storage_id` is a fixed lowercase base32 keyed digest of the
session-derived `owner_user_id`, calculated by the backend with a dedicated
storage-key secret (for example HMAC-SHA-256 with domain separation). It is
directory-safe, nonreversible without that secret, and never accepted from a
request. It is not the login name, raw `owner_user_id`, tenant/body field, or
an unkeyed hash. Rotating the storage key requires an explicit offline
rekey procedure and is not a runtime fallback. `binding.json` is immutable
after issuance and contains the project key, normalized workflow top-level
folder, and creation time; it is not a second current-revision pointer. A
revision file contains the schema version, project key, revision, business
fields, and update time. `current.json` is the sole atomically replaced current
revision record. The issuance record binds the issuance request ID to the
normalized request digest and issued key. The binding index contains only the
folder digest and project key needed for explicit recovery.

All writes use a same-directory temporary file, restrictive permissions,
file `fsync`, atomic replace, and parent-directory `fsync`. A process lock plus
compare-and-swap revision check serializes writers. An update first publishes
the immutable revision file and only then atomically replaces `current.json`.
A crash before the second step leaves an unreferenced revision file that is
ignored; it never advances current state. Revision files are immutable after
their atomic publish. Symlinks, hard links outside the store, path traversal,
noncanonical UUIDs, and records whose embedded owner/project binding does not
match their directory are rejected. Recovery reads the binding index and then
revalidates `binding.json`; it never trusts the index alone or scans another
owner directory.

### Copy, Save As, import, and rebind matrix

| Operation                                                           | Key rule                                                               | Context rule                                                                                      |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Duplicate or Save As inside the same top-level folder               | Retain the existing key.                                               | Both workflows read the same latest context for future submissions.                               |
| Rename a workflow inside the same top-level folder                  | Retain the existing key.                                               | No rebind. Existing queued snapshots remain pinned.                                               |
| Save As into another top-level folder                               | The copied node is treated as mismatched and cannot run.               | User must invoke `rebind_as_new_project`; a new key and blank draft are issued. No context copy.  |
| Official template copied to a new top-level folder                  | Issue a new key through `official_template_copy`.                      | Create a blank draft, then use the existing first-workflow save path.                             |
| External JSON loaded without a persisted workflow locator           | Treat every embedded key as untrusted/unbound for this import session. | User must explicitly initialize/rebind after choosing the target path; no automatic context copy. |
| Existing persisted workflow reopened                                | Resolve its key against owner and top-level binding.                   | Recover the current revision; do not issue a key.                                                 |
| Node key accidentally removed in an existing bound top-level folder | Explicit `recover` may return the unique owner-scoped binding.         | Recovery writes the recovered key only after user confirmation. Ambiguity never guesses.          |
| Key belongs to another owner or record is absent                    | Do not attach it.                                                      | Offer initialization of a new blank project; reveal no foreign context.                           |

The extension may mark an imported/unpersisted graph as requiring explicit binding through widget-owned ephemeral state during existing extension load hooks. It does not modify Workflow management and does not intercept the later save. Backend owner/top-level validation remains the final gate.

## Execution-only Workflow locator serialization

The saved Project Context node contains only `project_key`, but every prompt
must also prove which persisted Workflow path is currently active. The
frontend extension reads (never mutates) the existing active Workflow's
canonical `path` and installs an execution-only `workflow_locator` widget/input
on the backend-defined Project Context node:

- `widget.serialize = false`, so LiteGraph Workflow persistence omits the
  locator;
- `widget.options.serialize` remains enabled, so existing `promptInputs`
  includes it;
- `widget.serializeValue` returns the active persisted Workflow path at prompt
  construction time;
- an unsaved/temporary/missing path returns an invalid-unbound marker that the
  backend rejects; it never guesses a folder;
- the extension does not intercept Save, rename, duplicate, import, or
  autosave and does not write any Workflow store field.

This is execution evidence, not authority. Prompt admission still binds the
session-derived owner, `project_key`, server project record, and normalized
top-level folder. A client-supplied locator alone cannot rebind a project.

Fan-out snapshot fields use the same nonpersistent widget mechanism:
`beforeQueued` selects the in-memory reference/run tuple, and
`serializeValue` returns that tuple to `graphToPrompt`. No persistent
`widget.value` is changed, so a concurrent save cannot capture an ephemeral
reference, run key, or lease. With no active fan-out session, these serializers
return the explicit inactive form and never read or advance the reference
cursor.

## Prompt snapshot semantics

“Latest project settings” is resolved at prompt admission, not when a queued job eventually begins execution.

For each accepted `/prompt` submission, the backend custom-node package validates and pins:

- `project_key`;
- immutable `project_context_revision`;
- normalized `workflow_locator` and project top-level binding;
- immutable ReferenceSelection revision;
- `fanout_request_id`, reference ID, logical ordinal, and the fan-out action's unique `run_key` when fan-out is active.

The prompt-admission hook stores or injects this pin in server-side prompt data before acceptance. A worker resolves context and selection by the pinned revisions. Later context/selection edits affect only later submissions. Already accepted Queue items never observe those edits, even if they have not started.

The frontend preflight obtains the latest revision receipts for cost/capability display. The backend re-resolves and pins authoritatively at each prompt acceptance. The browser cannot force an unowned revision. If authoritative state changed after preflight, admission either pins the newer valid state consistently for that action or rejects with a retryable stale-preflight error; it never mixes revisions within one accepted prompt.

For a fan-out batch, preflight obtains a short-lived server snapshot lease. All N accepted prompts must pin the same project-context and ReferenceSelection revisions. An expired or conflicting lease stops further submissions and produces M/N reconciliation. The lease is not persisted into the saved workflow and is not an execution state machine.

## Fan-out ownership and state

Only the `레퍼런스 선택` backend custom node's `선택 항목 실행` widget action may create an active fan-out session. The state is held in the widget/extension closure (or a `WeakMap` keyed by that widget), not in `ComfyApp`, Pinia, Workflow management, Queue, or LiteGraph classes. It is not serialized to a saved workflow.

Normal Run, Shift+Run, Auto Queue, partial execution, and existing Batch Count can still cause the host to call widget callbacks. When `fanout_active` is false, both callbacks return without reading or writing fan-out/reference values. They do not infer fan-out from node presence, selected-reference count, Batch Count, trigger source, graph shape, or workflow name.

## Start and preflight

The widget action performs these steps before setting `fanout_active`:

1. Require a persisted, owner-bound workflow and valid Project Context key.
2. Resolve required PROJECT_CONTEXT fields and pin-able context/ReferenceSelection revisions.
3. Validate node connections, executable media availability, rights/capability, nonempty selected references, uniqueness, expected cost/time, and the fixed one-job-per-reference rule.
4. Present the exact N, expected cost/time, queue position, and confirmation. Existing UI Batch Count is ignored for fan-out and is never multiplied by N.
5. Refuse to start while another frontend prompt submission is being admitted. This prevents `ComfyApp.queuePrompt`'s existing “already processing” return path from detaching this widget session from its queued request. The extension may use existing public submission events/UI state, but it may not read private fields or patch global controls.
6. Call the prepare endpoint and accept its snapshot lease, server-issued
   `fanout_request_id`, and one server-issued UUID `run_key` for the whole
   action. A malformed run key or a missing/extra/duplicate reference fails
   before session activation.
7. Preserve `logical_reference_ids` in the user-confirmed order. Set `ordered_reference_ids` to that order for queue back (`0`) and to its reverse for queue front (`-1`).
8. Activate the widget-owned session and call exactly once:

```ts
await app.queuePrompt(session.queue_position, session.expected_count)
```

It never calls `queuePrompt` N times.

## Callback algorithm

### `beforeQueued`

If no active session exists, return immediately with no mutation.

For an active session:

1. Assert `cursor < expected_count`, `accepted_count === cursor`, and no unresolved in-flight reference.
2. Read `ordered_reference_ids[cursor]` without advancing `cursor`.
3. Resolve that reference's logical ordinal and the action's server-issued run
   key.
4. Place one ephemeral `FanoutIterationSnapshot` in the widget-owned closure
   read by the custom node's nonpersistent prompt serializers.
5. Set `in_flight_reference_id` to that reference.

`graphToPrompt` then captures that exact reference/run snapshot for one
independent prompt. The ephemeral values may appear in the Queue's submitted
prompt/workflow snapshot, but the saved source Workflow never receives them.

### `afterQueued`

If no active session exists, return immediately with no mutation.

For an active session, this callback is the only place that advances submission state:

1. Require `in_flight_reference_id === ordered_reference_ids[cursor]`.
2. Append that reference to the accepted receipt.
3. Increment `accepted_count` by one.
4. Increment `cursor` by one.
5. Clear `in_flight_reference_id`.

The current host calls `afterQueued` only after its awaited API submission path reaches `queuedCount++`. The backend `/prompt` contract must return a nonempty `prompt_id` for every accepted response; an HTTP 200 response without `prompt_id` is a contract failure and must not be treated as valid backend behavior.

The Omarketing callback is synchronous, bounded, allocation-minimal, and
non-throwing. It catches its own invariant error, marks local reconciliation
required, and returns so it cannot break later widget callbacks. Its receipt is
provisional: an earlier sibling widget callback can still prevent it from
running after the server accepted the prompt.

A job later failing, being cancelled, or being interrupted does not roll back `cursor`: admission success and execution success are different facts.

## Queue-front correction

The existing API maps `number === -1` to repeated front insertion. Repeatedly inserting A, then B, then C at the front produces C, B, A. Therefore the fan-out submission order is reversed only for front insertion:

| User/logical order | Queue position | `ordered_reference_ids` submitted | Final relative Queue order        |
| ------------------ | -------------: | --------------------------------- | --------------------------------- |
| A, B, C            |     `0` (back) | A, B, C                           | A, B, C                           |
| A, B, C            |   `-1` (front) | C, B, A                           | A, B, C, ahead of the prior queue |

User-facing M/N receipts and retry lists are always returned to logical order, regardless of submission order.

## Submission failure and M/N reconciliation

If prompt construction, validation, authentication, workspace consistency, `/prompt`, a widget invariant, any widget callback, Queue UI refresh, or snapshot lease validation fails:

- the extension calls the reconcile endpoint before declaring which reference
  failed or may be retried;
- `M` is the server-authoritative accepted tuple count and `N = expected_count`;
- accepted references remain ordinary Queue jobs and are not cancelled or resubmitted automatically;
- unsubmitted references are the logical-order set difference between selected
  references and authoritative accepted receipts;
- the UI reports `M/N queued` plus the unsubmitted references and a safe failure reason;
- retry is an explicit new action with a new fan-out request ID and one new
  action run key, pre-populated only with unsubmitted references;
- execution failures after admission remain in existing Queue/History and do not use this submission reconciliation path.

The widget action catches both a rejected `queuePrompt` promise and a resolved
non-success result, compares callback receipts with server receipts, and
reconciles conservatively. During the live loop only `afterQueued` advances the
cursor. Final server reconciliation may increase the immutable outcome receipt
when a prompt was accepted before a sibling callback/UI failure, but it never
resumes the old loop or mutates widget values.

If authoritative reconciliation is unavailable, the result is
`submission_outcome_unknown`, not a guessed `M/N`. No reference is automatically
retryable until a later reconciliation proves it was never accepted.

## Session cleanup

The action uses `try/finally`. On complete submission, partial submission, thrown error, workflow switch, node removal, widget teardown, logout/backend switch, or explicit pre-admission cancel, cleanup:

1. clears in-flight serializer snapshot/reference/run/lease data and asserts
   that no persistent widget value was changed;
2. replaces the session with `{ fanout_active: false }`;
3. releases its submission lease and event listeners;
4. retains only the user-visible immutable outcome receipt needed by the
   dialog/toast.

Cleanup is idempotent. It does not remove accepted Queue items, delete outputs, clear ReferenceSelection, change Batch Count, or call interrupt/cancel. Reloading a workflow can never resume a fan-out session.

## Distinct prompt/output tuple invariant

For one fan-out action:

- all reference IDs are unique;
- one canonical `run_key` is unique to the fan-out action and is shared by its
  accepted reference prompts;
- each accepted prompt contains exactly one reference ID and that action run
  key;
- no two accepted prompts share `(fanout_request_id, reference_id)` or
  `(run_key, reference_id)`;
- each reference job owns exactly five candidate branches indexed `0..4` inside that job, not five Queue jobs;
- every produced candidate has a unique `OutputTuple(project_key, workflow_locator, run_key, reference_id, candidate_index)`;
- the backend derives `reference_storage_key` as `r-` plus the full lowercase
  hex HMAC-SHA-256 of a domain-separated
  `(project_key, run_key, reference_id)` tuple using a backend storage secret,
  and writes candidates under
  `<run_key>/references/<reference_storage_key>/candidates/`; filenames and
  subfolders preserve the full tuple without exposing the raw reference ID or
  overwriting another tuple;
- all five branches must succeed for the reference job to complete; partial files may remain under existing output/cache behavior, but History-backed Assets visibility is not guaranteed for a failed job.

The backend validates the tuple before writing. Cache keys may reuse upstream computation but cannot collapse distinct output tuples or cause two reference jobs to share a final output locator.

## Prohibited designs

- passive Workflow-save interception to issue, recover, or rewrite a project key;
- folder name as identity or context embedded into every workflow;
- automatic context copy across top-level folders or external imports;
- a frontend Project/Run/Asset store replacing existing stores;
- a global `queuePrompt` wrapper, monkey patch, or new Queue loop;
- fan-out inferred during normal Run/Shift+Run/Auto Queue;
- `queuePrompt` called once per reference;
- fan-out N multiplied by existing Batch Count;
- cursor advance in `beforeQueued`, before API acceptance, or from the final boolean result;
- frontend cancellation/rollback of already accepted jobs after M/N failure;
- a human-input node that pauses one Comfy execution;
- frontend synthetic IDs as persisted selection/output authority.
